# Background job notices TUI design

Slice N1 of T1b. It closes the release gate of H5 ([roadmap](../260930-2254-pi-feature-inventory-go-roadmap/roadmap.md), H5 status and T1b; [H5 plan](../261010-2349-h5-builtin-tools/plan.md), decision N1).

## 1. Outcome

When a background job finishes, the harness sends the model a user message wrapped in `<system-reminder>` (`internal/jobs/notice.go`). Today the TUI draws that message as a user prompt and as a `next` queue row, so the user sees text that they did not type.
After this change the TUI never shows a system reminder as a prompt or a queue row. A finished job shows as one job line in scrollback, in the tool line pattern, and the agent's answer to it follows. While jobs run, the status rail shows how many run when nothing else uses the rail.
This holds for the leader TUI and the in-process TUI, which use the same translator and session view.

## 2. Non-goals

- No new ACP method. The TUI learns about jobs from the events it already receives (tool results and the notice messages). A client that attaches to a session after a job started does not know that job until its notice comes (open question 2).
- No job list dialog, no `/jobs` command, no key to kill a job. The model has `job_list`, `job_output` and `job_kill`.
- No change to the text that the model receives. Hiding is in the TUI only.
- `session/close` on the leader wire is a separate protocol gap (open question 3).
- Tool output expand (T-LAY-09) and truncation display (T-MD-10) stay in their own T1b slice.

## 3. Placement

| What | Where | Replaces |
|---|---|---|
| Job line | Scrollback, one row, where the notice prompt was drawn | The `❯` prompt band of the notice and its empty row after it (an empty row follows the job line, as after a tool line) |
| Notice in the queue | Not drawn | The `┆ ⧗ next  <system-reminder>…` row. When only notices are queued, the queue block, hint included, uses no rows |
| Job count | Status rail (`┊`), lowest priority: shown only when no other state uses the rail | Nothing; today an idle session has an empty rail |
| Job count while the agent works | Tail of the `Working…` rail row: ` · 1 job` | Nothing |

The job line uses the tool line pattern of the style guide: `  ● job <id>  <label>` with the status right-aligned.
The status comes from the notice: `✓ completed · exit 0` (success), `✗ failed · exit 2`, `✗ failed · signal: SIGSEGV`, `✗ killed · <reason>` (error). A monitor notice shows `<n> events` (muted); its event lines go to the model only.
A system reminder that is not a job or monitor notice uses no row at all.

## 5. States and transitions

The session view keeps a set of known jobs: id, label and state. Only events change it.

| State | Trigger | Next state |
|---|---|---|
| No job known | Tool result with `details.jobId` and `details.status: running` (background `bash`, `monitor`, or a `bash` call that passed its wait budget) | Job known, running (S1). Label = the short arguments of that tool line |
| Job running | A notice user message names the job (`Background job <id> (…) finished [status: …]`) | Job line appended to scrollback (S4, S7); job removed from the running set |
| Job running | A `job_output` or `job_kill` tool result for the job with a final `details.status` | Job removed from the running set; no job line (the model asked; there is no notice) |
| Job running | A monitor notice for the job | Job line `<n> events` appended (S8); the job stays running |
| Any | Session ends, or the TUI opens another session | Set cleared |
| Any | Link to the leader is lost | Rail shows the lost link as today; the set is kept and shown again after the reconnect |
| Notice queued | `queue_update` holds a reminder text | Reminder entries are left out of the queue rows (S5, S6) |
| Notice taken | `message_end` of the reminder user message | Job line instead of a prompt band (S4) |
| Notice unknown | Reminder text that matches neither notice form | No row; the agent's answer still follows |

Edge cases:

- Stale result: a notice for an id that is not in the set (the TUI attached late) still draws the job line from the notice text alone.
- Two notices that the harness merges into one message (`internal/jobs` merges monitor events): one job line for each job in it.
- The agent's reply to a notice has no prompt above it; the job line is its context.

## 6. Keys and focus

No new key. Existing keys change only in what they see:

| Key | Receiver | Change |
|---|---|---|
| `alt+↑` (edit queue) | Pending input | Steps over hidden reminder entries; it never puts a reminder into the editor |
| `esc` (interrupt) | Session view | Unchanged; it does not stop jobs |
| `ctrl+c` | Root model | Unchanged |

The queue hint `alt+↑ edit queue` is drawn only when at least one visible row exists.

## 7. Limited space and resize

- The job count is the lowest-priority rail state: any other rail state (lost link, sending, error, notice, retry, cancelling, working, no model) hides it, except that `Working…` carries ` · N job(s)` in its tail.
- From 60 columns the idle rail is `┊ ◌ 1 background job · <id> <label>`; with more jobs, `┊ ◌ N background jobs · <id>, <id>`. The tail is cut with `…` at the terminal width.
- Under 60 columns the idle rail is `┊ ◌ N job(s)` and the working tail is ` · N job(s)` after `esc`.
- The job line follows the tool line rules: the status stays whole, the label is cut first, then the id.
- Under 4 rows only the editor and the status remain (layout rule); the job count may then use the status row.

## 8. Text and width

- The label is the short argument text of the starting tool line, one line, cut with `…` by columns. CJK and emoji count two columns.
- A failure reason or kill reason from the notice is cut with `…` before the label is cut away completely, as for a tool failure reason.
- Tabs and line breaks in a label become one space (the existing `oneLine`).
- Paths are not shortened beyond the cut.

## 9. Style intent

- Job line: glyph `●` in `tool`, `job <id>` in `tool` bold, label in `muted`, status in `success`, `error` or `muted`.
- Idle rail: `┊` in `dim`, `◌ N background job(s)` in `muted` (not `accent`: the agent is not working), the tail in `dim`. No shimmer.
- Working tail: ` · N job(s)` in `muted`, as the rest of the tail.
- No new glyph and no new color.

## 10. Acceptance criteria

1. At 80×24, after a background `bash` call returns while the agent becomes idle, the screen shows `┊ ◌ 1 background job · bash-1 npm run build` on the status row.
2. At 40×14, in the same state, the status row shows `┊ ◌ 1 job`.
3. At 80×24, after a second background job starts, the status row shows `┊ ◌ 2 background jobs · bash-1, bash-3`.
4. At 80×24, while the agent works and one job runs, the status row ends with `esc to interrupt · 1 job`.
5. At 80×24, after a job finishes with exit code 0 while the session is idle, scrollback shows `  ● job bash-1  npm run build` with `✓ completed · exit 0` right-aligned, and no row of the screen contains `system-reminder` or `Background job`.
6. At 80×24, after that notice, the status row no longer shows a job count.
7. At 80×24, after a job finishes while the agent works and the user queued `also check the lint`, the queue shows exactly one row `┆ ⧗ next    also check the lint` and the hint; no queue row contains `Background job`.
8. At 80×24, when only the notice is queued, no `┆` row is drawn.
9. At 80×24, after `alt+↑` in that state, the editor does not contain `system-reminder`.
10. At 80×24, a failed job shows `✗ failed · exit 2` and a killed job `✗ killed · timeout`, in the error role.
11. At 80×24, a monitor notice with three events shows `  ● job bash-2  tail -f server.log` with `3 events`.
12. With the built `ask` and its leader, the background `bash` scenario of acceptance criterion 5 passes (E2E through the leader socket), and the same scenario passes with the in-process agent.

## 11. Open questions

1. **What does a finished job show?** Decided (user, 2026-10-12): A, one job line in scrollback, as in this design.
2. **Jobs that started before this client attached.** Decided (user, 2026-10-12): A, accept the gap; the notice still draws its job line. No new ACP method.
3. **`session/close` on the leader wire.** Decided (user, 2026-10-12): A, a separate small H13 slice right after N1; it removes the skip of `TestLeaderSessionCloseKillsBackgroundJobs`.
