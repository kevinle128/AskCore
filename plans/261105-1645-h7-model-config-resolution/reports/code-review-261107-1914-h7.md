## Findings

### F1. Medium: value command stdout is buffered with no size bound

- Where: `internal/app/auth_native.go:52-79` (`runValueCommand`, `Observe` writes every stdout chunk into a `bytes.Buffer`).
- Defect: The buffer has no cap. The only bound is the 10 s timeout in `auth.Values`.
- Failure scenario: A user writes `"apiKey": "!cat ~/.secrets"` and points it at a large file or a device by mistake, or a helper loops on output. The leader (one process for all local sessions) buffers up to 10 s of output at pipe speed, which is many GB. The leader can be killed by the OS memory limit, and every session and background job of the leader ends. A key or header value never needs more than a few KiB.
- Note: The sandbox ring buffer is bounded, but `Process.ingest` (`internal/sandbox/process.go:249-258`) calls `Observe` for every chunk, and `SpillFile` is nil here, so the copy in `runValueCommand` is the only one that grows.
- Fix: Stop at a fixed limit (for example 64 KiB). When a chunk passes the limit, return a plain failure (`failed (output too large)`) and let the context cancel the process. Add one test with a runner that writes more than the limit.

### F2. Low: user `baseUrl` is not parsed by the file loader

- Where: `internal/settings/models_file.go:170` reads `baseUrl` as any string; `internal/providers/model_config.go:186-189` copies it to the rows.
- Defect: No scheme or host check. The session log is safe: `Prepared.Endpoint` goes through `providers.EndpointOf` (`internal/providers/prepare.go:161-167`, no userinfo or query) and `modelRef` keeps only scheme and host (`internal/agent/request_log.go:50-58`). But `AuthSnapshot.String` (`internal/providers/auth.go:24`) prints the full `Endpoint` (= the user `baseUrl`), so any present or future log of a snapshot prints userinfo or a query key of the URL.
- Failure scenario: `"baseUrl": "proxy.example/v1"` (no scheme) gives no file problem; it fails only at the first request with a transport error, after the provider was shown as usable. `"baseUrl": "https://user:token@proxy.example/v1"` is accepted, and its token is in `AuthSnapshot.String` output.
- Fix: In the file loader, require `http` or `https` with a host and reject userinfo, as a provider problem whose text names the field only. Optionally print `EndpointOf(a.Endpoint)` in `AuthSnapshot.String`.

### F3. Low: `ModelsFiles.Load` can store an older read after a newer one

- Where: `internal/settings/models_files.go:71-114`.
- Defect: The read and parse run without the lock; the lock covers only compare and store. Two concurrent `Load` calls can finish in the other order: the call that read the old bytes stores last, its stamp differs, the generation increases, and the old content becomes current.
- Failure scenario: Not reachable today, because the only shared `ModelsFiles` is the refresher one and `modelRefresher.load` holds `loadMu` (`internal/app/model_refresh.go:224-226`), and `LoadModelView` makes its own instance. A future caller that calls `Load` directly on the refresher instance (for example from a request path or a second goroutine) gets a stale model table with a newer generation, so `ForgetAll` and the rebuild logic think they are up to date.
- Fix: Either document "callers must serialize Load" on the type, or re-stat under the lock and drop a result whose stamp is older than the stored one.

### F4. Low: `ConfigKey.Endpoint` check is always true; the binding guard lives only in `app`

- Where: `internal/app/session_models.go:418-423` (`configKey` sets `Endpoint: m.BaseURL` from the same row it binds to); `internal/auth/service.go` `configBinds` and `configSnapshot`.
- Defect: Not a bug today. The real guard is `userTables` keyed by `(Provider, API, BaseURL)`, which only holds rows of providers that the file names. The `Endpoint == m.BaseURL` check in `auth` cannot fail for any current caller, so `auth` gives no independent protection, although its doc comment says the key "binds only to a model row with the same BaseURL".
- Failure scenario: A later caller that builds a `ConfigKey` from a provider entry and a row of another source (for example a row from the account list after a refactor) passes the check automatically. The file key then goes to a URL that the user file did not write.
- Fix: Set `Endpoint` from the file entry (the `baseUrl` of the provider or model entry, or the built-in URL when the file sets none) in `userTables`, store it in `userEntry`, and pass that to `ConfigKey`. Then the `auth` check means what its comment says.

### F5. Low (docs): `--api-key` on a re-pointed provider needs a file `apiKey`

- Where: `internal/auth/service.go` `selectSource` (override path falls back to `configSnapshot` only when `req.Config != nil`); `internal/app/session_models.go:419-421` (`configKey` is nil when the entry has no `apiKey`); `docs/cli.md` `--api-key` row.
- Defect: The behavior matches phase 2 requirement 6 ("when the provider has a ConfigKey"). But M3(d) and the docs read as if any provider that the file re-points accepts `--api-key`. With `providers.anthropic.baseUrl` set and no `apiKey`, `ask -p --model anthropic/<id> --api-key K` ends in `auth: method ... anthropic/api-key` (ErrMethod).
- Failure scenario: A user who keeps the proxy key out of the file and passes it on the command line gets a method error with no hint.
- Fix: Add one sentence to the `--api-key` row and to the key order section of `docs/cli.md`: on a provider whose `baseUrl` the file changes, `--api-key` works only when the file entry also sets `apiKey` (any value form). Or, if the intent is the M3(d) wording, build a `ConfigKey` for every re-pointed endpoint with an empty value. That second option changes behavior and needs a user decision.

### F6. Medium (tests): the production command runner has no test

- Where: `internal/app/auth_native.go:47-80` (`runValueCommand`). `rg runValueCommand` finds only its definition and its use at `auth_native.go:39`; no test file names it. The `"!..."` values in the tests run through an injected `auth.RunCommand`.
- Defect: The parts that the docs promise are unproven on the real path: `sandbox.ShellArgv`, `Dir` = home, `Env` = full environment (a secret helper needs credential variables), non-zero exit to `*auth.ExitError` (so the error text holds only the code), the 10 s timeout returning `context.DeadlineExceeded` (so the reason is `timed out`), and stderr not reaching any error.
- Failure scenario: A later change of `sandbox.Run` (for example returning a result with a nil exit code on a kill instead of `ctx.Err()`) turns a timeout into `failed`, or a change that wraps stderr into `res.Err` puts helper output into an error text. The fake-runner tests still pass. This conflicts with the project rule that tests run the real code path.
- Fix: One test in `internal/app` that calls `runValueCommand` (or `ask -p` with a `models.json` `!command` and a temp `HOME`) for: `printf key` gives `key`; `exit 3` gives `*auth.ExitError{Code: 3}`; a variable from the parent environment is visible; `printf secret >&2; exit 1` gives an error whose text has no `secret`; a short deadline gives `context.DeadlineExceeded`.
