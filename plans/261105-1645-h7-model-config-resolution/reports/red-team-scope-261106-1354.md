# Red team: scope and contracts of the H7 plan

Date: 2026-11-06. Lens: Scope and Complexity Critic (Contract Verifier). Read: plan.md, decisions.md, phases 1, 4, 5, 7 (phase 2, 3 and 6 requirements only where other phases cite them). Requested scope (H-PROV-17, H-PROV-19, `--models`, `enabledModels`, cycling key, `--offline`) and the user decisions Q1-Q3, QA, QB, QD are constraints, not findings.

## Finding 1: Phase 1 forces a second copy of the hardened file readers
- **Severity:** High
- **Location:** Phase 1, section "Files" ("This phase does not touch `settings.go`") and Requirement 7.
- **Flaw:** The user and project file rules live in readers that end in `json.Unmarshal` into a map. They give no byte-level helper. Phase 1 must read JSONC bytes, so it cannot call them. Because `settings.go` is reserved for phase 6, the only path left is to write the rules again in `models_files.go`. The project rules are subtle: `EvalSymlinks`, a size check before the open, `openNoFollow` with `O_NONBLOCK`, and a second regular-file check after the open. The user rules also need `CheckPrivateDir` of the home and `checkEntry(path, 0600)` before the read.
- **Failure scenario:** The copy drops `O_NONBLOCK` or the second `IsRegular` check. A trusted repository commits `.ask/models.json` as a FIFO, or replaces it with one between the stat and the open. The leader blocks in `open` when a session reads its model list. Every later `models()` call of that leader waits on the lock of Finding 2. The settings reader is safe, but the models reader is not, and no test catches it, because the phase 1 test list has no FIFO or symlink case.
- **Evidence:** `internal/settings/settings.go:156-184` (`readSettings` ends in `json.Unmarshal` into `map[string]json.RawMessage`); `internal/settings/project.go:31-43` (rule comment) and `internal/settings/project.go:44-89` (`readProjectSettings`, `O_NONBLOCK` at line 62, `json.Unmarshal` at line 82); `internal/settings/settings.go:348-366` (`readUserFile` home and entry checks).
- **Suggested fix:** In phase 1, split each reader into a byte reader and a decoder: `readUserFileBytes(home, name)` and `readProjectFileBytes(path)`. The settings readers and the models reader then call the same byte readers. Phase 1 owns the small change in `project.go`, and the plan records a coordination point with phase 6 for the change in `settings.go` (or moves the extraction to phase 1 and lets phase 6 start after it). Add FIFO and symlink-loop cases to the phase 1 tests.

## Finding 2: The lock claim in Phase 1 is false, and one process lock serializes every project read
- **Severity:** Medium
- **Location:** Phase 1, Requirement 6 ("no I/O under the lock except the stat and read of that one file, which is the existing pattern of `Layered`"); Phase 5, Requirement 3 ("one process-wide `settings.ModelsFiles` keyed by path").
- **Flaw:** `Layered` takes no lock for a read. The plan cites a pattern that does not exist, and it puts file I/O under one mutex. Phase 5 then shares that one instance among all projects of all sessions of a leader.
- **Failure scenario:** One session works in a project on a slow network mount, or on the FIFO of Finding 1. Its read holds the mutex. A second session in another project opens `/model`, and its `models()` call waits on the same mutex. With Finding 3, each model request of every session also waits. One project stops the model list and the inference of all sessions of the leader.
- **Evidence:** `internal/settings/settings.go:246-252` (the `Layered` comment, line 249: "A read takes no lock, because each write replaces the file atomically"); `internal/app/model_refresh.go:206-213` (the refresher releases `loadMu` before it calls `Load`, so it does not do the check and the reload under one lock).
- **Suggested fix:** Stat and read outside the lock. Under the lock, compare the stamp and store the result only when it is newer. Correct the text of Requirement 6 so that it cites no pattern that does not exist.

## Finding 3: The per-request key lookup rebuilds the view on every model request, which D14 does not allow
- **Severity:** High
- **Location:** Phase 5, section "Data flow" (request line), Requirement 3 ("The view is built per call; it holds no state of its own"), Requirement 8 (`Models func() SessionModels` called by `AuthRunner`), and the Risk row "Per-call view build is slow".
- **Flaw:** `AuthRunner` calls the view function for each stream. Each call stats the project file, runs the D9 checks, and builds two merged `NewModelSet` values (set and catalog). D14 limits a reload to `/model` open and session start. With this design the reload happens on every model request, so it works like polling on each turn. Then the key, the headers and the D9 result can change during a turn with no user action.
- **Failure scenario:** A user edits `.ask/models.json` in the middle of a tool loop and saves an incomplete edit. The next request in the same run reads the new stamp. If the provider entry fails a cross-field rule, phase 1 drops it, the key table has no entry, and the request fails with no credential, or the next source (env) is sent instead. The user did not open `/model`, and the D14 contract says nothing reloads at that time. The cost also grows: a catalog with hundreds of rows is merged and sorted twice for each request.
- **Evidence:** `internal/app/module_auth.go:19-46` (the stream function runs once per request and calls `service.Resolve` each time); `internal/app/model_refresh.go:271-274` (lines 272-273: each build makes two `NewModelSet` values); `internal/providers/model_set.go:46-52` (`NewModelSet` clones and merges every row).
- **Suggested fix:** Build the session view at session start and again when `/model` opens (`models()`), store it in the session, and let `AuthRunner` read the stored key and header table. Change the Risk row: the cost is per request, not per list read.

## Finding 4: Two stamp layers and two `ModelsFiles` owners for one file set
- **Severity:** Medium
- **Location:** Phase 1, Requirement 6 (`ModelsFiles.Load` stats the file and keeps its own stamp); Phase 5, Requirement 2 (`modelRefresher` also stats `<ASK_HOME>/models.json` in `Load` and `reloadIfChanged`) and Requirement 3 (a second, process-wide `ModelsFiles` for project files).
- **Flaw:** The user file gets two stamps: one in `settings.ModelsFiles` and one in the `fileStamp` of the refresher. The plan has two `ModelsFiles` instances with different owners. That is a parallel structure for one job.
- **Failure scenario:** The refresher sees a new stamp for `models.json` and runs the full `Load`: it reads `model-cache.json` again and builds both sets again, although only the user file changed. Between the two stats, an editor writes the file again. The refresher stores the newer stamp, but `ModelsFiles` returns the copy of the first stat. The snapshot then holds the old rows until the next unrelated change, and `Values.ForgetAll` ran for a change that the snapshot does not show.
- **Evidence:** `internal/app/model_refresh.go:85-90` (`fileStamp`), `internal/app/model_refresh.go:195-213` (`Load` and `reloadIfChanged` compare the stamp of one file).
- **Suggested fix:** Use one `ModelsFiles` per process for the user file and the project files. Let `Load` return a generation number or a "changed" flag. The refresher compares that value and keeps `fileStamp` for `model-cache.json` only.

## Finding 5: The exact steps of `ResolvePattern` do the job of `findIn` again with other rules
- **Severity:** Medium
- **Location:** Phase 4, Requirement 2, steps 1-3 ("case-insensitive compare of provider and id"), and Steps 4 (new error types).
- **Flaw:** `findIn` already gives the exact `provider/id[@api]` lookup and the two-API ambiguity error, and `ModelSet.Find` and `acp.FindModel` use it. Phase 4 writes the exact steps again: they are case-insensitive and have new error types. M13 keeps `setModel` and saved defaults on the old exact and case-sensitive path. The result is two exact matchers and two parsers of `provider/id@api`, with different rules.
- **Failure scenario:** `enabledModels: ["OpenAI/GPT-5.5"]` or `--model Anthropic/claude-opus-4-5` resolves at start, because the new matcher ignores case. The TUI cycling key (phase 8) then sends the scope entry to `_ask/session/setModel`. If it sends the raw scope string and not the resolved row id, `parseModelID` and `findIn` refuse it as "unknown or ambiguous model". The two-API case has two error texts: `ambiguous model a/b: x and y` from `findIn` and the `ErrAmbiguousModel` list from phase 4.
- **Evidence:** `internal/providers/catalog.go:126-151` (`findIn`, case-sensitive, ambiguity text); `internal/providers/model_set.go:110-120` (`ModelSet.Find` uses it); `internal/acp/ask_methods.go:121-134` (`parseModelID`) and `internal/acp/ask_methods.go:240-247` (refusal text).
- **Suggested fix:** Let steps 1-3 call `findIn` for the exact match. Use the case-insensitive match only in the fuzzy step. Make `acp.parseModelID` call the `provider/id@api` part of `ParsePattern`, so that one grammar exists. State in phase 6 that `ACPScopedModel.ModelID` is the resolved `ModelID(row)`, never the raw pattern.

## Finding 6: `ErrUnknownLevel` blocks the alias and fuzzy steps for every id that has a colon
- **Severity:** Medium
- **Location:** Phase 4, Requirement 3, and the table row `openrouter/qwen/qwen3:free`; decisions.md "Extension trace" (Ollama).
- **Flaw:** Requirement 3 says: a suffix that is not a level word and has no exact match gives `ErrUnknownLevel`. Ollama, vLLM and OpenRouter ids often end in a tag (`qwen3-coder:30b`, `qwen/qwen3:free`). Such a suffix is not a typo of a level. The rule makes the error name the wrong cause, and steps 4 and 5 (alias, fuzzy) never run for these ids. D11 ("unknown level is an error") is an accepted decision; the question is only which error wins when the suffix does not look like a level.
- **Failure scenario:** A user with the plan's own extension provider types `ask -p --model local/qwen3:30b` (the row is `qwen3-coder:30b`). The output is `unknown thinking level "30b"; valid: off, minimal, low, medium, high, xhigh, max`, not "unknown model" or a fuzzy match. The user looks for a thinking problem that does not exist.
- **Evidence:** `cmd/tui/args.go:97-100` (the seven level words); phase 4 table row `openrouter/qwen/qwen3:free` (no level word, the colon stays in the id).
- **Suggested fix (question for the user, not a cut):** Give `ErrUnknownLevel` only when the id without the suffix resolves (exact, alias or fuzzy). Otherwise run all steps on the full id and give `ErrUnknownModel`. Add `local/qwen3:30b` and `gpt-5.5:hgih` with a row `gpt-5.5` to the table, so both cases have a test.

## Finding 7: The new session-option fields have no validation and no owner for later list reads
- **Severity:** Medium
- **Location:** Phase 6, Requirement 7 (`ACPSessionOptions.Model`, `Thinking`, `Models`) and Requirement 8 (`models()` fills `Scope` "from the session options"); Phase 7, section "Context" (`ACPModelsResult.Scope`).
- **Flaw:** `flagsFromMeta` checks the prompt size and each tool name, because an ACP client is an external input. The plan adds three fields and names no check: no limit on the count or length of `Models`, and no check of `Thinking` against the level words. Phase 6 also does not say where the session keeps the raw `Models` patterns after start. `models()` needs them on each read to expand the scope again against a new view.
- **Failure scenario:** An editor ACP client sends `Models` with 10 000 glob entries. Each `/model` read runs `ExpandScope` over every row for each entry, under the session state, and the answer holds every match. A `Thinking: "ultra"` value enters the session with no error and fails later at the clamp or as a silent default. A newer TUI against a running leader of the same protocol that drops the field (phase 6 says an older peer ignores it) starts on the saved default with no notice that `--model` did not apply.
- **Evidence:** `internal/acp/session_options.go:24-50` (the existing checks: prompt bytes at line 41, tool names at lines 44-48); `pkg/protocol/acp_session.go:19-39` (`ACPSessionOptions`, `IsZero`); `internal/acp/agent.go:309-316` (the options are read once into `SessionRequest.Flags`).
- **Suggested fix:** Add checks in `flagsFromMeta`: a maximum count and length for `Models` and `Model`, and `Thinking` in the level list. Say in phase 6 that the session keeps the raw scope patterns next to its flags and that `models()` expands them against the stored view of Finding 3. State the behavior when the host does not echo the scope (the TUI shows a notice that `--model` was not applied).

## Finding 8: `KeySource` adds a second copy of the resolution order for a display that was not requested
- **Severity:** Medium
- **Location:** Phase 5, Requirement 12 (per-provider key source in `ask settings show`); Phase 2, Requirement 6 (`KeySource`).
- **Flaw:** The acceptance criteria ask that each problem shows in `ask settings show`. They do not ask for a key source per provider. `KeySource` must repeat the order and the binding-skip rules of `ResolveWith` (Phase 2 Requirement 4) without running a command or a refresh. That is a second implementation of the most security-relevant rule of the plan, and it can drift from the first.
- **Failure scenario:** `Resolve` accepts a saved `api-key` credential with no method check, while it checks the method of other credentials. `KeySource` copies the order but checks the method first, or adds the endpoint skip in a different place. `ask settings show` prints `config:$OLLAMA_KEY` for a provider while requests send the saved key, or the reverse. The user trusts the display and debugs the wrong source.
- **Evidence:** `internal/auth/service.go:129-140` (override first), `internal/auth/service.go:155-166` (saved `api-key` returns at line 160 before the method check at lines 162-165).
- **Suggested fix (question for the user):** Ask whether the per-provider key source belongs in H7. If it stays, make `ResolveWith` and `KeySource` share one function that returns the chosen source with a "dry run" flag, so one order exists. If it goes, `settings show` lists the models.json files and their problems only.
